# Запуск и отладка tg-digest

## Как устроен запуск

Штатный режим — контейнер с `serve`: в одном процессе планировщик и слушатель
команд в «Избранном». Каналы, курсоры и журнал доставки живут в базе
(`digest.db`), а не в конфиге и не в `state.json` — его больше нет.

**Публикует только демон** — по cron или по команде `/run`. Публикующего прогона
в CLI нет специально: два процесса над одной базой выдали бы два дайджеста.
CLI оставлен для отладки: `login`, `preview`, `run --dry-run`.

Пути по умолчанию ведут в volume контейнера (`/data`), поэтому локально каждой
команде нужен `--config config.toml`, а в самом конфиге — локальные
`session_file` и `db_file`.

## Перед запуском

Тулчейн: `cargo --version`. Если команды нет — установка в `README.md` (нужен
именно MSVC-линкер).

Рабочий конфиг: `config.toml` (не `config.example.toml`). Нет — скопировать
пример и назвать поля, которые заполняет владелец: `telegram.api_id`,
`telegram.api_hash`, `telegram.phone`, `anthropic.api_key`, `telegram.folder`.

**Никогда не выводить содержимое `config.toml`, `tg.session` и `digest.db`
в лог или в ответ** — там ключи, доступ к аккаунту и тексты дайджестов.

## Порядок проверки изменений

Идти строго по возрастанию цены ошибки. Следующий шаг — только после чистого
предыдущего.

| Шаг | Команда | Что проверяет | Цена |
|---|---|---|---|
| 1 | `cargo build` | компиляция | — |
| 2 | `cargo test` | разбор ответа, рендер, курсоры, оркестрация map-reduce | — |
| 3 | `cargo run -- --config config.toml preview` | состав папки, курсоры, склейку альбомов, отсечку коротких постов | бесплатно, LLM не вызывается |
| 4 | `cargo run -- --config config.toml run --dry-run` | качество дайджеста: слиты ли дубли, верны ли ссылки | стоит токенов, ничего не публикует |
| 5 | `serve` + `/run` при `destination = "me"` | публикацию целиком: разметку, разбиение, отсутствие превью | пост уходит в «Избранное» |
| 6 | `destination = "@channel"` | — | виден подписчикам |

Не предлагать шаг 6, пока владелец явно не сказал, что доволен результатом.

## Авторизация

`login` — интерактивная команда: ждёт код из Telegram со stdin, при 2FA ещё и
пароль. **Не запускать в фоне и не автоматизировать ввод.** Просить владельца
выполнить самому:

    ! cargo run -- --config config.toml login
    ! docker compose run --rm -it tg-digest login

Успех — появившийся `tg.session`; повторный `login` скажет «уже авторизованы».

## Контейнер

```bash
docker compose build             # первым делом на чистом окружении:
                                 # иначе login и preview уйдут в старый образ
docker compose up -d             # поднять
docker compose logs -f           # смотреть прогоны
docker compose stop              # мягкая остановка (SIGTERM, grace 30s)
docker compose kill              # SIGKILL без grace — только для сценариев обрыва
```

Состояние целиком в `./data`: `config.toml`, `tg.session`, `digest.db`.
Пересборка при работающем демоне — штатная (`up -d --build`), файл не залочен,
как это было бы на Windows.

## Команды в «Избранном»

`/help` — список. Управление каналами (`/add`, `/rm`, `/sync`), диагностика
(`/list`, `/status`), прогон (`/run`), повтор (`/last`) и разбор недоставленного
(`/resume N`, `/abandon N`).

Команды, которые трогают курсоры, отклоняются, пока идёт прогон, — это не
ошибка, а блокировка. При недоставленном прогоне разрешены только `/run`,
`/resume` и `/abandon`.

## Отладка расписания

Проверять на боевом cron бессмысленно — ждать сутки. Временно:

```toml
[schedule]
cron = "*/2 * * * *"
```

плюс `destination = "me"`, запустить `serve` и убедиться, что в логе есть «ждём
следующего прогона» с корректным временем, прогон стартует, а Ctrl+C гасит
демон. После проверки **вернуть боевой cron**.

Догон (`catch_up`): остановить демон, дождаться пропуска слота, запустить
снова — прогон должен произойти сразу.

Логи подробнее: `RUST_LOG=tg_digest=debug`.

## Сценарии восстановления (PLAN.md §9.7)

Проверяются только вживую, на настоящем Telegram. Ключевые:

- **Доставка после обрыва.** Дайджест из трёх частей, `docker kill` после
  первой → после старта в чате ровно три части без дублей, `runs.status = ok`,
  курсоры сдвинуты.
- **Адресат зафиксирован.** То же, но между стартами сменить `destination` →
  хвост уходит в старый чат, следующий прогон — в новый.
- **Устаревание.** Отодвинуть `first_send_at` выбранного недоставленного
  прогона на `publish_retry_window_hours + 1` часов назад → автоповтора нет,
  приходит одно уведомление с `/resume` и `/abandon`. Правку делать **на
  остановленном контейнере** и только для этого прогона:

  ```bash
  docker compose stop
  sqlite3 data/digest.db "SELECT id, status, first_send_at FROM runs
      WHERE status IN ('summarized','publishing');"       # выбрать N
  sqlite3 data/digest.db "UPDATE runs
      SET first_send_at = strftime('%Y-%m-%dT%H:%M:%SZ','now','-3 hours')
      WHERE id = N AND status IN ('summarized','publishing');"
  docker compose start
  ```

  Формат времени обязан остаться RFC3339 (`strftime`, а не `datetime`): иначе
  прогон упадёт на разборе времени из базы. `WHERE` с `status` — страховка от
  правки завершённого прогона.
- **Отозванная сессия.** «Завершить все другие сеансы» → контейнер выходит
  с ненулевым кодом, в логе просьба выполнить `login`, `docker ps` показывает
  рестарты.

Смотреть базу — только на чтение и только в остановленном контейнере:

```bash
sqlite3 data/digest.db "SELECT id, status, error, first_send_at FROM runs ORDER BY id DESC LIMIT 5;"
sqlite3 data/digest.db "SELECT id, title, enabled, last_msg_id, last_error FROM channels;"
```

## Типовые ошибки

**`link.exe not found`** — не поставлены VS Build Tools, см. `README.md`.

**Ошибки компиляции в `src/telegram/`** — почти всегда дрейф API grammers.
Crate pre-1.0, в 0.10 схема подключения переписана (`SenderPool` +
`Client::new(handle)`, `SqliteSession::open`, updates из `pool.updates`). Сверять
сигнатуры с <https://docs.rs/grammers-client/0.10.0/>, а не с примерами из
поиска — они под старый API.

**`нет авторизации в Telegram`** — выполнить `login`.

**`папка … содержит авто-правило`** — в папке включён флаг вроде «Каналы» или
«Непрочитанные». Состав такой папки вычисляемый, синхронизация отключена
намеренно: убрать флаг и вызвать `/sync`.

**`канал исключён из прогона`** — упёрлись в `max_posts_per_channel` или канал
не читается. Курсор не сдвинут, следующий прогон дочитает; поднять лимит или
сбросить канал через `/reset <id>`.

**FLOOD_WAIT** — слишком частые запросы. Поднять `pause_between_channels_ms`
и не ставить cron чаще, чем раз в несколько часов.

**HTTP 400 от Anthropic API** — чаще всего в запрос попал параметр, который
`claude-opus-5` не принимает (`thinking`, `budget_tokens`, `temperature`), либо
в JSON-схеме у объекта нет `additionalProperties: false`.

**`ответ обрезан по max_tokens`** — поднять `anthropic.max_tokens`.

**`сводки … не помещаются в один запрос`** — map-reduce не смог сжать вход даже
промежуточными заходами. Курсоры не сдвинуты; уменьшить `lookback_hours` или
число каналов.

**Ошибка компиляции внутри `grammers-crypto`** (`safe_prime::check`, `BigUint`) —
cargo подтянул `glass_pumpkin 2.0.0-rc1` вместо `rc0`. Лечится
`cargo update -p glass_pumpkin --precise 2.0.0-rc0`; поэтому `Cargo.lock` коммитится.

**`no method named html`** — отключилась фича `html` у `grammers-client`
(в `default` её нет), проверить `Cargo.toml`.

## Чего не делать

- Не обрезать вход молча при большом количестве постов: для этого есть
  map-reduce, а если и он не справился — падать с ошибкой. Тихая потеря
  половины каналов выглядит как рабочий дайджест.
- Не править `digest.db` руками, чтобы «перезапустить прогон»: для повторного
  прогона есть `--dry-run`, для сброса канала — `/reset`, для снятия
  недоставленного — `/abandon`.
- Не публиковать из CLI и не добавлять такую команду: публикует только демон.
- Не дописывать к id модели суффикс с датой.
