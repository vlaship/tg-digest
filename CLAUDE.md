# tg-digest

Сервис-демон: читает список Telegram-каналов через MTProto, суммаризирует посты
через Claude Messages API и постит дайджест обратно в Telegram по cron-расписанию.
Штатный режим — контейнер с `serve`; управление — команды в «Избранном».

Подробный замысел и порядок работ — в [PLAN.md](PLAN.md).

## Раскладка

| Файл | Отвечает за |
|---|---|
| `src/main.rs` | CLI (`login` / `preview` / `run --dry-run` / `serve`), планировщик, сигналы |
| `src/config.rs` | `config.toml` + env-оверрайды секретов, валидация |
| `src/db.rs` | SQLite: каналы с курсорами, журнал прогонов и доставленных частей |
| `src/run.rs` | прогон целиком, блокировка, восстановление недоставленного |
| `src/cancel.rs` | кооперативная остановка по SIGTERM / Ctrl+C |
| `src/schedule.rs` | croner: следующее срабатывание, догон пропущенных слотов |
| `src/telegram/client.rs` | подключение, логин, выборка постов по курсору |
| `src/telegram/folder.rs` | папка Telegram как список каналов: чтение, валидация, sync |
| `src/telegram/publish.rs` | отправка частей по `random_id`, журнал доставки |
| `src/telegram/commands.rs` | команды в «Избранном» (`/add`, `/run`, `/status`, …) |
| `src/summarize.rs` | HTTP-вызов Anthropic Messages API |
| `src/digest.rs` | JSON-схема ответа, проверка ссылок, рендер Telegram-HTML, разбиение |
| `Dockerfile`, `compose.yaml` | образ и запуск; всё состояние — в volume `/data` |

## Правила репозитория

**Секреты.** `config.toml` и `tg.session` в `.gitignore` и туда не возвращаются.
`tg.session` — это полный доступ к аккаунту Telegram, а не «просто кэш».
В репозиторий идёт только `config.example.toml`. При добавлении настройки —
дописать её и в пример, и в таблицу выше, если появился новый модуль.

**Правда о каналах — в базе и в папке Telegram,** не в конфиге. `[[channels]]` —
только seed для пустой базы; после первого запуска правки там ничего не меняют.
Названия и username перечитываются перед каждым прогоном (`refresh_channels`)
одним `channels.getChannels` — и с папкой, и без неё: переименованный канал иначе
навсегда останется в дайджесте со старой ссылкой.

**grammers 0.10.** Crate pre-1.0, API переписан относительно 0.7–0.9: подключение
идёт через `SenderPool` (`runner` крутится отдельной задачей, `Client::new`
принимает `handle`, updates забираются из `pool.updates`), сессия —
`SqliteSession::open`, а не файловая. Сигнатуры сверять с
<https://docs.rs/grammers-client/0.10.0/>, не по памяти и не по примерам из
поиска — они почти все под старый API.

**Anthropic API.** Модель берётся из конфига как есть, суффиксы с датой к id
не дописывать. На `claude-opus-5` thinking включён по умолчанию — параметры
`thinking`, `budget_tokens` и `temperature` не передавать (400). Структурированный
ответ — `output_config.format` с `type: "json_schema"`, во всех объектах схемы
обязателен `additionalProperties: false`.

**Никогда не обрезать вход молча.** Вход больше `LARGE_INPUT_CHARS` уходит в
map-reduce (`summarize.rs`): части сжимаются отдельными запросами, затем сводятся
общим system-промптом. Части режутся по каналам — канал разрывается, только если
сам не влезает в бюджет. Сводки, которые вместе снова не влезают в запрос,
сводятся промежуточно (до `MAX_REDUCE_STAGES` заходов). Перед финальным запросом
его промпт проверяется целиком (`ensure_fits`): не влез — прогон падает с явной
ошибкой, а не отправляет заведомо негодный запрос и не выбрасывает темы. Курсоры
при этом не двигаются, посты войдут в следующий прогон. Ссылки на посты обязаны
пережить шаг map — иначе своду нечего класть в `sources`, и всё вылетит на проверке. `max_posts_per_channel` —
предохранитель: канал, упёршийся в лимит, исключается из прогона целиком и курсор
не двигает.

**Репост помечается источником.** Без пометки «репост из: …» модель считает
репост и оригинал двумя новостями и не сливает их в один пункт.

**Курсоры двигаются одной транзакцией со статусом `ok` или `empty`.** До этого
они лежат в `runs.cursors` и на выборку не влияют: упавшая публикация не «съедает»
посты, которых никто не увидел. Пустой прогон — тоже успешный: посты прочитаны.

**Повторная отправка — только по сохранённому `random_id`.** Он выдаётся один раз
при записи части в журнал; `RANDOM_ID_DUPLICATE` — это доставка, а не ошибка.
Срок дедупликации у Telegram не документирован, поэтому за пределами
`publish_retry_window_hours` демон сам не повторяет: решает владелец (`/resume`).

**Порядок проверки изменений.** Сначала `preview` (без токенов), затем
`run --dry-run` (без публикации), и только потом демон с `destination = "me"`
и `/run` из «Избранного». Публикация в настоящий канал — последним шагом.
Реального прогона в CLI нет: публикует только демон, иначе два процесса над
одной базой выдадут два дайджеста.

## Грабли сборки (уже наступили)

**`Cargo.lock` коммитится.** `grammers-crypto` требует `glass_pumpkin = "2.0.0-rc0"`,
но по правилам semver для пре-релизов cargo подтягивает `2.0.0-rc1`, где сменили
API (`safe_prime::check` теперь возвращает `Result`) и подняли `num-bigint` до 0.5 —
сборка падает внутри зависимости. Версия закреплена в lock-файле:

```
cargo update -p glass_pumpkin --precise 2.0.0-rc0
```

Если после `cargo update` сборка вдруг сломалась в `grammers-crypto` — это оно.

**Фичи `html` и `parse_invite_link` у grammers-client включены явно.**
`InputMessage::html()` спрятан за `#[cfg(feature = "html")]`, а
`Client::accept_invite_link` — за `parse_invite_link`; в `default` их нет.
Без них ошибка выглядит как «no method named `html`».

**`libsql` берём тот же, что тянет `grammers-session`** (0.9, `default-features =
false`, фича `core`), иначе в бинарник приедет второй SQLite.

**Проверка перед коммитом:** `cargo fmt && cargo clippy --all-targets && cargo test`.
