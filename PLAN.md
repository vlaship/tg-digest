# tg-digest — сервис суммаризации Telegram-каналов на Rust

## Context

Нужен сервис-демон, который **по расписанию (cron)** читает список Telegram-каналов, делает
из них связный дайджест через Claude и постит его обратно в Telegram. Всё управление —
каналы, промпты, API-ключи, расписание — лежит в одном файле `config.toml`.

Ключевое ограничение, определившее архитектуру: **бот не может читать чужие каналы** —
его нужно добавлять админом в каждый. Поэтому чтение идёт через **MTProto с личного
аккаунта** (`grammers-client`), и он же используется для публикации — одна сессия на всё,
без BotFather.

Требование к формату: дайджест группируется **по темам**, и если несколько каналов пишут
об одном и том же событии — пункты **сливаются в один** с перечислением всех источников.

Проект новый: `C:\vs\prj` — песочница с подпроектами `go/ java/ py/ ts/`, добавляем `rust/`.

### Решения, зафиксированные с пользователем
| Вопрос | Решение |
|---|---|
| Чтение | MTProto, личный аккаунт (`grammers-client` 0.10) |
| Стек | Rust |
| Тулчейн | winget: rustup + MSVC Build Tools |
| Публикация | тот же аккаунт → «Избранное» (`me`) или свой канал |
| LLM | Anthropic Messages API, `claude-opus-5` |
| Запуск | демон с cron-расписанием в конфиге |
| Конфигурация | один `config.toml`: каналы, промпты, ключи, расписание |
| Формат | группировка по темам + слияние дублей между каналами |

### Что нужно знать про зависимости
- `grammers-client` / `grammers-session` **0.10.0** (2 июля 2026, автор — Lonami, автор Telethon).
  Чистый Rust, без TDLib и C/C++ зависимостей.
- Crate **pre-1.0, API переписан в 0.10** — сверено по docs.rs: подключение идёт через
  `SenderPool::new(session, api_id)` (поля `runner` / `handle` / `updates`), `runner.run()`
  крутится отдельной задачей, а `Client::new` принимает `handle`. Сессия — `SqliteSession::open`,
  файловой `Session::load_file_or_create` больше нет. `Chat` переименован в `Peer`.
  Единственный надёжный источник сигнатур —
  <https://docs.rs/grammers-client/0.10.0/>; сверяться там, а не по памяти и не по
  старым примерам из гугла.
- `croner` **4.0.0** — только парсинг и вычисление следующего срабатывания
  (`Cron::from_str("0 9 * * *")` → `find_next_occurrence(&now, false)`), цикл ожидания
  пишем сами. Взят вместо `tokio-cron-scheduler`: меньше зависимостей и полный контроль
  над логированием, ошибками джобы и догоном пропущенных запусков.
- Официального Anthropic SDK для Rust нет → Messages API дёргаем напрямую через `reqwest`
  (это штатный путь для языков без SDK).

она перекрывает значение из TOML — так же конфиг можно переиспользовать на другой машине
или в CI, ничего в нём не меняя.

## Шаг 3. `login` — разовая авторизация (`telegram/client.rs`)

1. `SqliteSession::open(&cfg.telegram.session_file).await?` → `SenderPool::new(session, api_id)`
   → `tokio::spawn(runner.run())` → `Client::new(handle)`.
2. Если `!client.is_authorized().await?`:
   `request_login_code(phone).await?` → код со stdin → `sign_in(&token, &code).await?`.
3. Обработать `SignInError::PasswordRequired(token)` → `rpassword::prompt_password` →
   `check_password(token, pwd).await?`. Без этой ветки аккаунты с 2FA не залогинятся.
4. Отдельного сохранения сессии не нужно: `SqliteSession` пишет на диск сама.

> ⚠️ `tg.session` — это **полный доступ к аккаунту**, эквивалент залогиненного клиента.
> В `.gitignore` с первого коммита, никогда не коммитить и не копировать наружу.

## Шаг 4. Сбор постов (`telegram/client.rs`)

Для каждого канала с `enabled != false`:
- `client.resolve_username(&username).await?` → `Peer` (может вернуть `None` — канал
  переименован/удалён: залогировать и продолжить, не падать на весь прогон).
- `client.iter_messages(peer).limit(max_posts_per_channel)` — идёт от новых к старым;
  останавливаемся, когда `msg.date() < since` **или** `msg.id() <= last_seen[channel]`.
- Пауза `pause_between_channels_ms` между каналами + backoff на FLOOD_WAIT.

Тонкости, которые надо заложить сразу (иначе дайджест поедет):
- **Альбомы**: несколько сообщений с одним `grouped_id` — это одна публикация. Склеивать
  в один `Post`, брать непустой caption, ссылку — на первое сообщение группы.
- **Репосты**: помечать исходный канал, чтобы слияние дублей ниже не считало их отдельными новостями.
- **Короткие/медийные посты**: отбрасывать, если текст короче `min_post_chars`.

Модель:
```rust
struct Post { channel: String, title: String, msg_id: i32,
              date: DateTime<Utc>, text: String, url: String }
```
`url` = `https://t.me/{username}/{msg_id}` — именно он идёт в источники дайджеста.

### state.json (`state.rs`)
```json
{ "last_run": "2026-09-08T06:00:00Z",
  "channels": { "durov": { "last_msg_id": 1234 } } }
```

## Шаг 5. Суммаризация (`summarize.rs` + `digest.rs`)

Один запрос `POST https://api.anthropic.com/v1/messages` на весь батч постов.

Заголовки: `x-api-key`, `anthropic-version: 2023-06-01`, `content-type: application/json`.

Тело:
```jsonc
{
  "model": "claude-opus-5",
  "max_tokens": 16000,
  "output_config": { "effort": "high", "format": { /* json_schema, см. ниже */ } },
  "system": "<cfg.prompts.system>",
  "messages": [{ "role": "user", "content": "<cfg.prompts.user_template с подстановками>" }]
}
```

- **Thinking включён по умолчанию** на `claude-opus-5` — параметр `thinking` не передаём.
  Не передавать `budget_tokens` (400) и не задавать `temperature` (400 на этой модели).
- **Structured outputs** через `output_config.format` — просим JSON, а не готовый markdown:
  рендер в Telegram-HTML делаем сами, это надёжнее, чем чинить разметку от модели.
  ```jsonc
  { "topics": [ { "title": "...", "summary": "...",
                  "sources": [ { "channel": "...", "url": "..." } ] } ],
    "tldr": ["...", "..."] }
  ```
  Схема живёт в коде (это контракт парсинга), текстовые инструкции — в `[prompts]` конфига.
- **Объём**: если суммарный текст постов > ~400 000 символов, переходить на map-reduce
  (сначала сжать по каналам, затем свести) — иначе одного запроса хватает с запасом,
  контекст модели 1M.
- Прогон раз в сутки, поэтому **prompt caching бесполезен** (TTL 5 минут) — не закладывать.
- Обработка ответа: проверять `stop_reason` **до** чтения `content` (`"refusal"` возможен),
  парсить `content[] | type=="text"` через `serde_json`, а не регулярками.
- Ошибки: раздельные ветки на 429 (retry по `retry-after`), 5xx (backoff), 400/401 (падать
  с внятным сообщением) — одна общая ветка `is_err()` тут теряет разницу между «повторить»
  и «неверный ключ».

**Ориентир по стоимости**: 20 каналов × ~30 постов × ~500 симв. ≈ 300 тыс. символов ≈
120 тыс. токенов входа. На `claude-opus-5` ($5/$25 за 1M) это ≈ **$0.6–0.8 за прогон**,
~$20/мес при ежедневном запуске. Модель и `effort` вынесены в конфиг — понижать при
желании можно там, отдельная правка кода не нужна.

## Шаг 6. Публикация (`telegram/publish.rs`)

- Рендер `Digest` → Telegram HTML: `<b>тема</b>`, текст, строка источников
  `<a href="url">канал</a> · <a href="url">канал</a>`.
- **Лимит 4096 символов на сообщение** — резать по границам тем, а не вслепую по символам;
  длинный дайджест уходит серией сообщений.
- Отправка: `client.send_message(peer, InputMessage::html(chunk).link_preview(false))`.
  Превью выключаем — иначе Telegram подтянет картинку первой ссылки на весь пост.
- Цель: `destination = "me"` → пир текущего аккаунта (Избранное); иначе
  `resolve_username(&dest)`.

## Шаг 7. Планировщик (`schedule.rs`) и режимы запуска

CLI:
| Команда | Что делает |
|---|---|
| `tg-digest login` | разовая авторизация в Telegram |
| `tg-digest preview` | собрать посты и показать статистику, **без вызова LLM** |
| `tg-digest run [--dry-run]` | один прогон здесь и сейчас |
| `tg-digest serve` | демон: крутится по `[schedule].cron` |

Цикл `serve`:
1. `Cron::from_str(&cfg.schedule.cron)?` — 5-полевой формат; таймзона из конфига через
   `chrono_tz::Tz::from_str`, время считаем в ней (иначе «09:00» уедет на UTC).
2. **Догон**: при старте, если `catch_up = true` и следующее срабатывание после
   `state.last_run` уже в прошлом, — прогнать немедленно (ПК спал/демон был выключен).
   Плюс `run_on_start` для отладки.
3. `let next = cron.find_next_occurrence(&now_tz, false)?` → `tokio::time::sleep_until(...)`.
   Спать **не одним длинным sleep до next**, а тиками по ~60 с с пересчётом: длинный sleep
   на ноутбуке переживает засыпание непредсказуемо и приводит к пропуску запуска.
4. Прогон в `tokio::select!` с `tokio::signal::ctrl_c()` — Ctrl+C гасит демон, не убивая
   идущую отправку на середине.
5. **Ошибка прогона не роняет демон**: логируем, `last_run` не двигаем, ждём следующего
   срабатывания. Падать целиком — только на неустранимом (нет авторизации, битый конфиг).

Автозапуск демона на Windows — задача Task Scheduler «при входе в систему»:
```powershell
schtasks /Create /TN "tg-digest" /SC ONLOGON `
  /TR "C:\vs\prj\rust\tg-digest\target\release\tg-digest.exe serve"
```
Само расписание дайджеста при этом живёт в `config.toml`, а не в Task Scheduler —
правка cron не требует пересоздания задачи. Логи через `tracing-subscriber` в файл.

## Verification

Порядок именно такой — каждый шаг проверяется без риска спама в канал.
Локально каждой команде нужен `--config config.toml`: дефолты путей ведут в
volume контейнера (`/data`). Реального публикующего прогона в CLI нет —
публикует только демон, поэтому пункты 6–9 идут уже через `serve` и `/run`.

1. `cargo --version` — тулчейн встал, линкер найден.
2. `cargo build` — компиляция; здесь же вылезет дрейф API grammers 0.10, сверяем с docs.rs.
3. `cargo run -- login` — ввод кода из Telegram (и пароля 2FA, если включён).
   Успех: создан `tg.session`, повторный запуск не просит код.
4. `cargo run -- preview` — **без вызова LLM**: печатает, сколько постов собралось по
   каждому каналу и первые строки. Проверяем состав папки, курсоры, склейку
   альбомов, отсечку коротких постов.
5. `cargo run -- run --dry-run` — полный прогон с LLM, результат в stdout/`out/digest.html`,
   **без отправки и без записи в базу**. Проверяем главное: слиты ли дубли между
   каналами, корректны ли ссылки на исходные посты.
6. `serve` при `destination = "me"`, затем `/run` в «Избранном» — первый реальный
   пост уходит туда же. Проверяем HTML-разметку, разбиение длинного дайджеста,
   отсутствие превью, ответ `/status` с токенами.
7. Повторный `/run` сразу же — должен сказать «постов 0» и оставить статус `empty`
   (проверка курсоров в базе).
8. Планировщик: временно `cron = "*/2 * * * *"` + `destination = "me"` — убедиться,
   что прогон стартует по расписанию, логируется, а Ctrl+C гасит демон корректно.
   Затем вернуть боевой cron.
9. Догон: остановить демон, подождать пропуск слота, запустить снова при `catch_up = true` —
   прогон должен произойти сразу.
10. Только после этого — переключить `destination` на реальный канал и поднять
    контейнер (`docker compose up -d --build`), см. пункты 11–26 в 9.7.

- **grammers 0.x**: сигнатуры могут не совпасть с ожидаемыми; лечится сверкой с

- **Секреты в `config.toml`**: `.gitignore` до первого коммита, в репозиторий идёт только

## Шаг 8. Что не учли в плане (ревизия 2026-09-15)

Найдено при сверке плана с кодом. Это не «не доделали», а «не подумали»: пункты,
которых в шагах 1–7 нет вообще. Приоритет: **[A]** сломает прод или испортит
дайджест, **[B]** неудобно/дорого, **[C]** когда-нибудь.

### Выборка постов

- **[A] Приватные каналы.** Конфиг принимает только `username`, а `resolve_username`
  работает лишь для публичных. Канал по инвайт-ссылке (`t.me/+…`), на который аккаунт
  подписан, подключить нельзя. Нужно: `id = -100…` как альтернатива `username`
  (брать пир из диалогов / `PeerRef` по id), ссылка `https://t.me/c/{id}/{msg_id}`.
- **[A] `max_posts_per_channel` режет вход молча** — прямое нарушение правила из
  CLAUDE.md. Если канал за окно выдал 150 постов, 50 старых пропадают, а `last_msg_id`
  перепрыгивает через них навсегда. Минимум — `warn!` при упоре в лимит; правильно —
  лимит только как страховка от чтения всей истории, а не как отсечка дайджеста.
- **[A] Догон теряет посты.** Остановка идёт по `date < since` **или** `id <= last_seen`,
  и `since = now − lookback_hours`. После трёх дней сна ПК `catch_up` прогонит дайджест,
  но только за последние 24 ч — двое суток постов выпадут, хотя `last_msg_id` их видит.
  Решение: если `last_run` есть, окно = `max(lookback_hours, now − last_run)`.
- **[B] `last_msg_id` двигается по отфильтрованным постам, а не по максимальному
  прочитанному id.** Для альбома это `msg_id` первой части; остальные части выше
  указателя и на следующем прогоне читаются заново, но без первой (там `break`) —
  если подпись была не в первой части, альбом попадёт в дайджест второй раз.
  Двигать указатель на максимальный id, который видели, независимо от фильтра.
- **[B] Ссылки внутри текста теряются.** `message.text()` отдаёт голый текст, URL
  из text-entity («подробнее — тут») пропадают. Модели полезен `message.html()`
  (фича `html` уже включена) или список URL из entities отдельной строкой.
- **[C] Отредактированные посты.** Указатель по id не перечитывает правки. Осознанно
  не поддерживаем; зафиксировать как ограничение.

### Ответ модели

- **[A] Валидация `sources[].url`.** Промпт просит «не придумывай URL», код не
  проверяет. Сверять каждый `url` с множеством URL собранных постов; чужие —
  выкидывать с `warn!`. Заодно защита от prompt-injection в тексте постов:
  структурированный вывод + проверенные ссылки = модель не может утащить читателя
  на произвольный адрес.
- **[A] Пустой дайджест.** `topics = []` сейчас уходит в Telegram сообщением из
  одного заголовка. Не публиковать; состояние двигать (посты прочитаны, просто
  ничего важного).
- **[B] Логировать `usage`** (`input_tokens`, `output_tokens`) из ответа — иначе
  ориентир «$0.6–0.8 за прогон» не с чем сверить. Сюда же: следить, не упираемся ли
  в `max_tokens` из-за thinking при `effort = "high"` — по `stop_reason` в логах.
- **[B] `escape` не экранирует `"`** — URL с кавычкой ломает `href`. Закрывается
  валидацией выше (пропускаем только URL из своего набора).

### Демон и надёжность

- **[A] Рабочий каталог у Task Scheduler — `System32`.** `config.toml`, `state.json`,
  `tg.session` заданы относительными путями → задача ONLOGON не найдёт конфиг.
  Либо абсолютные `--config` / `--state` и абсолютный `session_file`, либо запуск
  через `cmd /c "cd /d C:\vs\prj\rust\tg-digest && target\release\tg-digest.exe serve"`.
  Обязательно проверить на шаге 10 верификации.
- **[A] Сессия отозвана (`AUTH_KEY_UNREGISTERED`, «завершить все сеансы» в Telegram).**
  Сейчас демон будет молча падать каждый прогон до бесконечности. Распознавать
  ошибку авторизации и **выходить** с внятным сообщением — это неустранимое, а не
  «ошибка одного прогона».
- **[A] Уведомление об ошибке.** Ночной прогон упал — узнаем через неделю из логов.
  Клиент Telegram уже есть: при ошибке прогона слать короткое сообщение в `me`
  («дайджест не собран: <ошибка>»). Дешевле любого мониторинга.
- **[B] Два экземпляра одновременно** (`serve` из Task Scheduler + ручной `run`):
  оба читают `state.json`, оба публикуют, один затирает состояние другого.
  Lock-файл рядом со `state.json`.
- **[B] `last_run` не двигается, если постов нет** (`run_once` выходит раньше) →
  `catch_up` при каждом рестарте после тихого дня гоняет пустой прогон. Считать
  «нечего публиковать» успешным прогоном и писать `last_run`.
- **[B] Частичная публикация.** Часть 2 из 3 не ушла → состояние не двинулось →
  следующий прогон опубликует часть 1 ещё раз. Ретраить отправку каждой части
  (FLOOD_WAIT/сеть) до того, как сдаваться; при окончательном провале — уведомление.
- **[B] Пересборка при работающем демоне.** Windows держит `.exe` залоченным —
  `cargo build --release` упадёт. Либо останавливать задачу перед сборкой, либо
  копировать бинарник в отдельный каталог и на него указывать в schtasks.
- **[C] Даты в локальной зоне.** Заголовок «Дайджест за DD.MM.YYYY» и `{{now}}`
  считаются в UTC; вечерний прогон по `America/New_York` получит завтрашнюю дату.
  Брать `schedule.timezone`. Заодно строки «Дайджест», «Коротко» вынести в
  `[prompts]`/конфиг — сейчас захардкожены в `digest.rs`.
- **[C] Лимит 4096 считается в UTF-16 code units,** а `chars().count()` считает
  scalar values: emoji = 2 юнита. Запас в 196 символов покрывает обычный дайджест,
  но при обилии эмодзи может не хватить — считать через `encode_utf16().count()`.

## Шаг 9. Docker, база и управление каналами из Telegram (решено 2026-09-15, ревизия после ревью)

### Решения

| Вопрос | Решение |
|---|---|
| Где живёт сервис | Docker-контейнер, `restart: unless-stopped`, один процесс `serve` |
| Хранилище | SQLite через **`libsql`** — он уже в дереве зависимостей (`grammers-session` → `libsql 0.9.30`), второй SQLite в бинарник не тянем |
| Что в базе | каналы (с `peer_id`/`access_hash`), курсор `last_msg_id` по каналам, прогоны и **части дайджеста с фактом доставки** |
| Что в `config.toml` | секреты, cron, промпты, модель, лимиты — то, что правится при деплое |
| Управление каналами | **вручную собранная папка в Telegram** как источник списка + **команды в «Избранном»** того же аккаунта |
| Бот | не нужен: бот не читает каналы, а UI для одного владельца даёт сам аккаунт. Добавляется позже как второй клиент над той же базой, если появятся другие пользователи |
| CLI | **только** `login` и отладочные `preview` / `run --dry-run`. Команд управления каналами в CLI нет |

Шаг 9 реализован кодом (см. «Статус на 2026-09-15» ниже): `state.json` убран,
появились `db.rs`, `run.rs`, `cancel.rs`, `telegram/folder.rs`,
`telegram/commands.rs`, `Dockerfile` и `compose.yaml`. Пункты Шага 8, помеченные
«закрывается по дизайну», теперь закрыты кодом, но **не проверены вживую**:
каждый проверяется пунктом верификации в 9.7, а он требует запущенного Telegram.

### 9.1 Docker

```
Dockerfile        # multi-stage: rust:1-bookworm → debian:bookworm-slim
compose.yaml      # volume /data, restart: unless-stopped, stop_grace_period: 30s
```

- Все рабочие файлы — в volume `/data`: `config.toml`, `tg.session`, `digest.db`.
  Пути в конфиге абсолютные (`session_file = "/data/tg.session"`), CLI-дефолты
  `--config /data/config.toml`. Это закрывает по дизайну пункт про рабочий каталог
  из Шага 8.
- `rustls` уже стоит → OpenSSL в образе не нужен. Alpine/musl не берём: `libsql`
  компилирует C-шный SQLite, с musl лишние приключения. `debian:bookworm-slim` +
  `ca-certificates`.
- **`login` — интерактивный, один раз**: `docker compose run --rm tg-digest login`
  (нужен `-it`, stdin для кода и пароля 2FA). Дальше сессия лежит в volume.
- **Логи в stdout**, Docker собирает сам. Пункт «логи в файл» из Шага 7 снимается.
- `catch_up = true` — штатный режим: перезапуск контейнера ≡ «ПК спал».

#### Остановка (SIGTERM / Ctrl+C)

Правило: **обрывать можно всё, что не записано; нельзя терять то, что записано
наполовину.** Единственная операция, которую нельзя прервать, — отправка одной части
дайджеста (секунды). Всё остальное либо идемпотентно, либо восстанавливается из базы.

- Сигнал → `CancellationToken` (`tokio_util`). `select!` на верхнем уровне **не
  оборачивает прогон**: прогон получает токен и сам проверяет его в контрольных
  точках — между каналами при сборе, перед вызовом LLM, между частями при
  публикации.
- Сбор постов прерван → ничего не записано, прогон помечается `error: cancelled`,
  курсоры не тронуты. Следующий слот соберёт заново.
- **Запрос к LLM прерываем** (`select!` на токен вокруг HTTP-запроса): токены
  потрачены зря, но в базе ничего нет, повтор безопасен. Ждать окончания нельзя —
  при `effort = "high"` ответ идёт минуты, любой разумный `stop_grace_period`
  не покроет.
- Публикация: текущая часть дописывается и фиксируется в базе, дальше — стоп.
  Прогон остаётся в статусе `publishing`, добивается на следующем триггере (9.3)
  с теми же `random_id` — при SIGKILL посреди отправки дубль возможен только если
  Telegram уже забыл `random_id` (9.3, «Устаревание»).
- `stop_grace_period: 30s` в compose. SIGKILL после него ≡ падение контейнера —
  сценарий восстановления тот же, что в 9.3, ничего специального.
- Ctrl+C и SIGTERM (`tokio::signal::unix`, под `#[cfg(unix)]`) — один и тот же
  токен. Второй сигнал — немедленный выход.

### 9.2 База (`src/db.rs`)

```sql
CREATE TABLE channels (
  id          INTEGER PRIMARY KEY,          -- peer id канала (положительный, без -100)
  access_hash INTEGER NOT NULL,
  username    TEXT,                          -- NULL у приватных
  title       TEXT NOT NULL,
  enabled     INTEGER NOT NULL DEFAULT 1,
  last_msg_id INTEGER NOT NULL DEFAULT 0,    -- 0 = ещё не читали, окно по lookback_hours
  last_error  TEXT,                          -- ошибка последнего сбора, NULL если ок
  added_at    TEXT NOT NULL
);

CREATE TABLE runs (
  id            INTEGER PRIMARY KEY,
  started_at    TEXT NOT NULL,
  finished_at   TEXT,
  status        TEXT NOT NULL,   -- collecting | summarized | publishing | ok | empty | error
  trigger       TEXT NOT NULL,   -- cron | catch_up | manual
  posts         INTEGER, topics INTEGER,
  input_tokens  INTEGER, output_tokens INTEGER,
  error         TEXT,
  cursors       TEXT,            -- JSON {channel_id: max_id_seen}: применить при status → ok | empty
  first_send_at TEXT,            -- время ПЕРВОЙ попытки отправки: от него считается устаревание (9.3)
  dest_label    TEXT,            -- "me" | "@channel" из конфига на момент прогона, для /status
  dest_peer_id  INTEGER,         -- разрешённый пир назначения: восстановление шлёт СЮДА,
  dest_access_hash INTEGER       -- а не в то, что сейчас в конфиге
);

CREATE TABLE run_chunks (
  run_id      INTEGER NOT NULL REFERENCES runs(id),
  idx         INTEGER NOT NULL,
  html        TEXT NOT NULL,
  random_id    INTEGER NOT NULL, -- random_id для messages.sendMessage; один на часть, навсегда
  delivered_at TEXT,             -- факт доставки. NULL = не подтверждена. ЭТО критерий завершения
  sent_msg_id  INTEGER,          -- id сообщения, если Telegram его вернул; только метаданные
  PRIMARY KEY (run_id, idx)
);
```

- `state.json` и `src/state.rs` **уходят**. `last_run` для планировщика =
  `MAX(started_at) FROM runs WHERE status IN ('ok','empty')`. Пункт «`last_run`
  не двигается на пустом прогоне» из Шага 8 закрывается по дизайну статусом `empty`.
- **Курсоры двигаются одной транзакцией со статусом `ok` или `empty`.** `ok` —
  после доставки последней части. `empty` — когда после сбора и фильтра постов нет
  **или** модель вернула `topics = []`: публиковать нечего, но посты прочитаны, и
  курсоры **успешно собранных** каналов применяются той же транзакцией (каналы,
  исключённые предохранителем или ошибкой, не трогаем). Без этого короткие и
  «неважные» посты перечитывались бы каждый прогон. До перехода курсоры лежат в
  `runs.cursors` и на выборку не влияют. Упавшая публикация не «съедает» посты
  (правило из CLAUDE.md).
- Курсор канала = **максимальный id, который видели при сборе**, независимо от
  фильтра по длине и склейки альбомов (баг с альбомами из Шага 8).
- `runs.*_tokens` и `/status` закрывают по дизайну пункты Шага 8 про `usage` и про
  «узнаем через неделю».
- `peer_id + access_hash` → выборка по `PeerRef` без `resolve_username`. Это даёт
  **приватные каналы** (пункт [A] из Шага 8). Ссылка на пост:
  `https://t.me/{username}/{id}` для публичных, `https://t.me/c/{peer_id}/{id}`
  для приватных.
- Миграции: таблица `schema_version`, миграции — `&[&str]` в коде, применяются
  при старте.
- `[[channels]]` в TOML — **только seed**: при пустой таблице импортируем и пишем
  в лог, дальше правда — в базе и в папке. В `config.example.toml` так и подписать.

### 9.3 Сбор и публикация: границы и восстановление

#### Границы сбора — курсор канала, а не глобальное время

- Канал с `last_msg_id > 0`: читаем **все** сообщения до `id <= last_msg_id`.
  Дата не участвует. Канал, который три дня падал, пока остальные шли, при
  восстановлении отдаст все три дня — глобальный `last_run` для границы **не
  используется** (идея `max(lookback, now − last_run)` из Шага 8 отменяется).
- Канал с `last_msg_id = 0` (новый, или сброшенный): окно `now − lookback_hours`.
- **Повторное включение** канала (`enabled` 0 → 1 через папку или `/add`) —
  курсор сбрасывается в 0. Иначе канал, выключенный на месяц, при возврате
  принесёт месяц постов.
- `max_posts_per_channel` — **предохранитель, а не отсечка**. Дефолт 1000. Если
  упёрлись в него, не дойдя до курсора/окна: канал в этом прогоне **исключается**,
  курсор **не двигается**, `channels.last_error` = «превышен лимит N, поднимите
  `max_posts_per_channel` или сбросьте канал через `/reset`», то же — в уведомление.
  Дайджест по остальным каналам публикуется. Молчаливой потери постов нет ни при
  каком значении лимита.
- Ошибка чтения канала (FLOOD_WAIT после backoff, сеть) — то же самое: исключить,
  курсор не трогать, `last_error`, уведомить. Следующий прогон дочитает с курсора.

#### Публикация — журнал доставки на `random_id`

Идемпотентность даёт сам Telegram: `messages.sendMessage` принимает `random_id`
«для предотвращения повторной отправки» — повтор с тем же `random_id` в пределах
серверного окна дедупликации не создаёт второго сообщения. Срок этого окна
**не документирован**, поэтому это снижение риска, а не гарантия; остаточный риск
дубля ограничивается политикой устаревания ниже. `random_id` генерируется **один
раз при записи части в журнал** и переиспользуется во всех ретраях, включая
ретраи после рестарта.
Никакого сравнения текстов: сверка «последних N сообщений» отброшена — часть могла
уйти за пределы окна, а старый одинаковый дайджест — совпасть ложно.

Реализация: высокоуровневый `send_message` в grammers `random_id` не принимает —
слать через `client.invoke(messages::SendMessage { random_id, peer, message,
entities, no_webpage: true, .. })`, разметку получать из того же HTML-парсера
(`grammers_client::parsers::parse_html_message` — сверить с docs.rs 0.10).

1. Ответ LLM получен → одной транзакцией: `runs.status = summarized`, `posts`,
   `topics`, `*_tokens`, `cursors`, **разрешённое назначение** (`dest_label`,
   `dest_peer_id`, `dest_access_hash` — резолвим `destination` из конфига именно
   здесь) и **все части** в `run_chunks` с `random_id`, `delivered_at = NULL`.
   С этого момента ни дайджест, ни адресат **не пересчитываются** — смена
   `destination` в конфиге и рестарт не уводят хвост в другой чат.
2. `status = publishing`. Части с `delivered_at IS NULL` шлём по порядку в
   `dest_peer_id`. Исход `invoke` трактуем так:
   - **успех** → `delivered_at = now`, `sent_msg_id` = id из ответа, если он там
     есть (`updateShortSentMessage.id` / `updateNewChannelMessage`; для некоторых
     пиров id в ответе нет — это нормально);
   - **`RANDOM_ID_DUPLICATE`** → сообщение с этим `random_id` у Telegram **уже
     есть**, id он не отдаёт. Это **доставка**: `delivered_at = now`,
     `sent_msg_id = NULL`. Не ошибка, не ретрай;
   - **неясный исход** (таймаут, обрыв, ошибка без кода) → ничего не пишем, повтор
     с **тем же `random_id`** через backoff; следующий ответ попадёт в одну из двух
     веток выше;
   - **явная ошибка** (`CHAT_WRITE_FORBIDDEN`, `PEER_ID_INVALID`, FLOOD_WAIT после
     backoff…) → прогон остаётся `publishing`, уведомление, правило ниже.
   Отправка части не отменяется токеном остановки.
3. **Критерий завершения — `delivered_at` у всех частей**, а не `sent_msg_id`.
   Выполнен → одной транзакцией: `status = ok`, `finished_at`, применить `cursors`
   к `channels.last_msg_id`. `sent_msg_id` нигде не участвует в логике — только
   в `/status` для справки.

После `MAX_ATTEMPTS` неясных исходов подряд прогон остаётся в `publishing`,
уведомление в Избранное, дальше — правила ниже.

**Незавершённый прогон блокирует новый сбор.** Проверка `runs WHERE status IN
('summarized','publishing')` выполняется **на каждом триггере** — старт `serve`,
cron, догон, `/run`, — а не только при запуске. Нашли → новый сбор **не
начинается** ни при каком исходе: курсоры не сдвинуты, повторный сбор дал бы те
же посты и второй дайджест. Что делать с найденным прогоном, решает его возраст.

**Устаревание.** `runs.first_send_at` пишется перед **первой** попыткой отправки
первой части и больше не меняется. Дедупликация по `random_id` у Telegram
ограничена по времени, и **срок не документирован** — мы на него не опираемся.
`publish_retry_window_hours` (дефолт **2**, `[telegram]`) — это **настраиваемая
политика повтора, а не граница безопасности**: внутри окна демон повторяет
доставку сам, принимая остаточный риск дубля за владельца; за его пределами —
только владелец. Значение 2 выбрано как компромисс между «покрыть ретраи внутри
прогона и перезапуск контейнера» и «не повторять после того, как сервер лежал
выходные»; ничем, кроме здравого смысла, оно не подкреплено, и дубль внутри окна
**возможен**, если окно Telegram короче.
- `now − first_send_at ≤ окно` → автоматически добиваем доставку (шаги 2–3 с теми
  же `random_id` и `dest_peer_id`). `/run` отвечает «есть недоставленный прогон
  #N, повторяю доставку» и делает только это.
- `now − first_send_at > окно` → **автоповтор не выполняется**. Прогон остаётся
  `publishing`, уведомление в Избранное (один раз, не на каждом триггере):
  «прогон #N не доставлен с <first_send_at>, безопасность повтора не гарантирована:
  `/resume N` — доставить недоставленные части (возможен дубль, если Telegram уже
  забыл `random_id`), `/abandon N` — снять». Демон ждёт решения владельца; cron
  тем временем пропускает слоты с `warn!`.
- `first_send_at IS NULL` (упали между `summarized` и первой отправкой) — возраст
  считаем от `started_at`, правило то же.

Ручные выходы — оба под блокировкой (9.5):
- `/resume <run_id>` — владелец принимает риск дубля; доставка идёт с сохранёнными
  `random_id` (лучший шанс на дедупликацию, если срок ещё не вышел), `first_send_at`
  не меняется — второе устаревание не наступит, но и не нужно: после `/resume`
  либо `ok`, либо явная ошибка и новое уведомление.
- `/abandon <run_id>` — `status = error: abandoned`, курсоры **не применяются**
  (доставленные части остаются в чате, посты войдут в следующий дайджест —
  владелец решает, что хуже).

Автоматического «сдаться» нет; автоматического «рискнуть» — тоже.

Прогон в статусе `collecting` при старте (упали до ответа LLM) — `error:
interrupted`, курсоры не тронуты, ничего не блокирует.

Пункт Шага 8 «частичная публикация → дубли» закрывается по дизайну этим журналом
**в пределах окна повтора**; за его пределами дубль остаётся осознанным решением
владельца через `/resume`. Проверка — 9.7 п. 17, 20–22, 26.

### 9.4 Список каналов = вручную собранная папка в Telegram

```toml
[telegram]
folder = "Digest"     # имя папки (dialog filter) в аккаунте
```

Папка в Telegram — это не только `include_peers`. У `dialogFilter` есть флаги
автовключения (`contacts`, `non_contacts`, `groups`, `broadcasts`, `bots`),
исключения (`exclude_muted`, `exclude_read`, `exclude_archived`), `pinned_peers`,
`exclude_peers`; бывают `dialogFilterChatlist` (общие папки) и `dialogFilterDefault`.
Папка «все каналы» (`broadcasts = true`, `include_peers = []`) при наивном чтении
выглядит пустой — и выключила бы всё.

Решение: **поддерживаем только явно собранную папку** и проверяем это.
- Sync (перед прогоном и по `/sync`): `messages.getDialogFilters` (raw TL через
  `client.invoke`, сверить с docs.rs grammers-client 0.10 / grammers-tl-types),
  фильтр по `title`.
- **Валидация**: любой из флагов автовключения или исключения установлен →
  sync **отказывается**: `warn!` + сообщение в Избранное «папка Digest содержит
  авто-правила (broadcasts), уберите их — синхронизация отключена», база остаётся
  как есть. `dialogFilterDefault` — то же самое. `dialogFilterChatlist` принимаем:
  у него только явные списки.
- Состав = `pinned_peers ∪ include_peers` **минус** `exclude_peers`, только
  `InputPeerChannel`. Пиры приходят сразу с `access_hash`.
- В базу: есть в папке → upsert, `enabled = 1` (0 → 1 = сброс курсора, см. 9.3);
  есть в базе, нет в папке → `enabled = 0`. **Не удаляем.**
- Папки не существует → `warn!` + уведомление один раз, работаем по базе.
  Папка валидна и пуста → явное «выключить всё», прогон со статусом `empty`.
- Добавить канал = подписаться и перетащить в папку с телефона. Убрать = вытащить
  из папки. Приватные каналы работают из коробки.

### 9.5 Команды в «Избранном» (`src/telegram/commands.rs`)

Демон слушает updates (`SenderPool.updates`; в 0.10 это отдельное поле пула —
сигнатуры сверить с docs.rs) и реагирует **только** на сообщения, у которых
`outgoing == true` и чат — сам аккаунт (`peer.id == me.id`). Никто, кроме владельца
аккаунта, туда написать не может, отдельная авторизация не нужна.

Каналы в командах адресуются **по `@username` или по числовому `id`** — у приватных
username нет. `/list` и ответ на `/add` всегда показывают `id`.

| Команда | Действие |
|---|---|
| `/add @channel` · `/add <t.me/+ссылка>` | резолв (для инвайта — `messages.importChatInvite`) → добавить в **папку** (`messages.updateDialogFilter`) → sync. Ответ: `title`, `id` |
| `/rm @channel` · `/rm <id>` | убрать из папки → sync (`enabled = 0`) |
| `/list` | `id`, название, `@username` или «приватный», вкл/выкл, курсор, `last_error` |
| `/reset <id>` | курсор в 0 (перечитать окно `lookback_hours`), `last_error` очистить |
| `/run` | прогон немедленно, `trigger = manual`. Идущий прогон → «уже идёт» |
| `/status` | последний прогон: время, статус, посты/темы, токены, ошибка; каналы с `last_error` |
| `/last` | переотправить части последнего прогона со статусом `ok` в **текущий** `destination`, с новыми `random_id` — это осознанный повтор, не восстановление |
| `/resume <run_id>` | доставить устаревший недоставленный прогон, приняв риск дубля (9.3) |
| `/abandon <run_id>` | снять блокировку недоставленного прогона: `error: abandoned`, курсоры не применяются (9.3) |
| `/sync` | перечитать папку (с валидацией из 9.4) |
| `/help` | список команд |

- Единый источник правды — **папка**. `/add` и `/rm` правят папку, а не базу,
  иначе следующий sync откатит правку. Если `folder` в конфиге не задан — команды
  правят базу напрямую.
- Ответ — сообщением в тот же чат. Ошибки команд — туда же, не в лог.
- **Одна блокировка на всё, что трогает курсоры и статус прогона.**
  `tokio::sync::Mutex<()>` держится на протяжении всего прогона (сбор → LLM →
  публикация, включая финальную транзакцию) и берётся через `try_lock` — никто не
  ждёт в очереди. Под ней же выполняются `/reset`, `/abandon`, `/sync`, `/add`,
  `/rm` (sync сбрасывает курсоры при 0 → 1) и `/last`. Заменяет lock-файл из
  Шага 8: процесс один, второго экземпляра в контейнере нет.
  - Блокировка занята (прогон идёт) → команда **отклоняется** сразу: «идёт прогон
    #N, повторите после». Не откладываем: отложенный `/reset`, сработавший через
    пять минут, удивит сильнее, чем отказ. Cron-слот, попавший на идущий прогон,
    пропускается с `warn!`.
  - Есть **незавершённый прогон** (`summarized`/`publishing`, блокировка свободна)
    → `/reset`, `/sync`, `/add`, `/rm` тоже отклоняются: «есть недоставленный
    прогон #N — `/run` для доставки или `/abandon N`». У такого прогона в
    `runs.cursors` лежат курсоры, которые при доставке перезапишут любой сброс.
    Разрешены только `/run` (= доставить, если прогон не устарел), `/resume`
    (доставить устаревший) и `/abandon`.
  - `/resume` и `/abandon` применяются **только к незавершённому, не идущему**
    прогону — под блокировкой, так что издатель не может параллельно довести его
    до `ok`.
  - `/list`, `/status`, `/help` — только чтение, без блокировки.
- Уведомления в Избранное: ошибка прогона, канал исключён из-за предохранителя
  или ошибки чтения, папка не прошла валидацию. Клиент уже есть, стоит ноль.
- Update-цикл и планировщик — две задачи в одном процессе, `Client` клонируется.
  Отозванная сессия (`AUTH_KEY_UNREGISTERED`) роняет обе → процесс выходит с
  ненулевым кодом, Docker его рестартует, в логах — что делать (`login`).
  Рестарт-луп здесь допустим: он виден в `docker ps`, тихий демон — нет.

    → `status = empty`, курсор канала сдвинут на максимальный id, повторный `/run`
    их не перечитывает. Канал, исключённый предохранителем в том же прогоне, — курсор
    на месте.
24. **`RANDOM_ID_DUPLICATE` = доставка**: часть доставлена и подтверждена; вручную
    вызвать `invoke` с тем же `random_id` ещё раз → Telegram отвечает
    `RANDOM_ID_DUPLICATE` (или возвращает то же сообщение) → обе ветки дают
    `delivered_at`, второго сообщения в чате нет, прогон доходит до `ok`, следующий
    триггер **не** заблокирован. Отдельно: чанк с `delivered_at`, но `sent_msg_id =
    NULL` — `/status` показывает его как доставленный.
25. **Команды не гоняются с публикацией**: во время идущего прогона `/reset <id>`,
    `/abandon`, `/sync`, `/add`, `/rm`, `/last` → «идёт прогон #N», база не изменилась;
    `/list` и `/status` отвечают. При незавершённом (не идущем) прогоне `/reset` →
    отказ с подсказкой; `/abandon N` → следующий `/reset` проходит, курсор 0 и не
    перезаписывается, потому что прогон N больше не доставляется.
26. **Долгий простой**: три части, `docker kill` после первой, в базе вручную
    отодвинуть `first_send_at` на `publish_retry_window_hours + 1` ч назад, старт →
    части 2–3 **не отправлены**, прогон остался `publishing`, одно уведомление
    «`/resume N` / `/abandon N`»; следующий cron-слот — `warn!`, второго уведомления
    нет, нового прогона в `runs` нет. `/resume N` → части 2–3 ушли (с сохранёнными
    `random_id`), `status = ok`, курсоры применены. Повторить сценарий с
    `/abandon N` → `error: abandoned`, курсоры на месте, следующий `/run` собирает
    те же посты.
